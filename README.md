## اصل معماری
AK1 یک اپلیکیشن مخصوص **مربی** است و هر مربی فقط به **حلقه خودش** دسترسی دارد.
نام حلقه (مثلاً «ابوتراب ۳») نباید در آیکون‌های منوی دسته‌ها یا ساختار عمومی رابط کاربری hard-code شود؛ نام حلقه باید از اطلاعات حساب/حلقه خوانده شود.

ساختار مفهومی:
```
مربی
└── حلقه خودش
    ├── اعضا
    ├── امتیازها
    ├── جلسات
    ├── تراشکاری
    └── رتبه‌بندی اعضا
```

## ورود و هویت حلقه

### حالت آنلاین
هنگام ثبت‌نام مربی:
- نام حلقه را خودش تعیین می‌کند.
- نام کاربری حلقه را خودش تعیین می‌کند.
- رمز عبور تعیین می‌کند.
- در آینده ورود به حساب با نام کاربری حلقه + نام حلقه + رمز عبور انجام می‌شود.
- داده‌ها باید فقط در محدوده همان حلقه قابل دسترسی باشند.

### حالت آفلاین
- برای استفاده محلی نیازی به تعیین رمز عبور نیست.
- اطلاعات روی دستگاه نگهداری می‌شود.
- در تنظیمات امکان **خروجی گرفتن از اطلاعات** وجود دارد.
- خروجی باید شامل داده‌های لازم برای بازگردانی کامل وضعیت حلقه باشد.
- در دستگاه/نصب دیگر، مربی می‌تواند فایل خروجی را از تنظیمات وارد کند و اطلاعات حلقه را **بازگردانی** کند.
- فرمت خروجی باید نسخه‌دار باشد تا در آینده امکان مهاجرت داده‌ها حفظ شود.

## دسته‌های اصلی برنامه

## وضعیت فعلی
نسخه پایه پروژه برای تست Android Studio ساخته شده است. ظاهر فعلی موقت است؛ ابتدا سازه، مدل داده و منطق کامل می‌شوند و طراحی نهایی رابط کاربری در مرحله پایانی انجام خواهد شد.

## معماری نسخه‌های آینده (فعلاً غیرفعال)

قرار نیست اپ اعضا یا اپ مدیر، از روی نام یا شماره تلفن حدس بزند هر فرد کیست. هنگام آماده‌شدن نسخه آنلاین، هویت‌ها با شناسه‌های پایدار و ارتباط‌های صریح به هم وصل می‌شوند:

- **مجموعه (Organization):** شناسه مستقل مجموعه.
- **حلقه (Ring):** متعلق به یک مجموعه؛ دارای مربی مسئول و اعضای خودش.
- **حساب عضو (Member Account):** پس از تأیید هویت، به یک رکورد عضو در یک حلقه متصل می‌شود؛ عضو فقط اطلاعات خودش را می‌بیند.
- **حساب مدیر (Manager Account):** به مجموعه متصل است و فقط حلقه‌هایی را می‌بیند که مدیر مجموعه صریحاً به او واگذار کرده است.
- **نقش‌ها و مجوزها:** عضو، مربی حلقه، مدیر مجموعه و مدیر سامانه دسترسی‌های جدا دارند؛ پنهان‌کردن دکمه در UI به‌تنهایی امنیت محسوب نمی‌شود و سرور هم باید هر درخواست را مجوزسنجی کند.

### روند اتصال پیشنهادی

1. مدیر مجموعه در پنل خود حلقه‌ها را ایجاد می‌کند یا درخواست اتصال یک حلقه را تأیید می‌کند.
2. هر حلقه یک شناسه داخلی پایدار دارد؛ کد دعوت یک‌بارمصرف و زمان‌دار فقط برای اتصال اولیه استفاده می‌شود و جای رمز عبور را نمی‌گیرد.
3. مربی از داخل حساب خود، عضو را به حلقه اضافه می‌کند و برای او کد اتصال شخصی می‌سازد.
4. عضو یا سرپرست او، طبق سیاست احراز هویت مجموعه، اتصال را تأیید می‌کند؛ سپس حساب عضو به همان شناسه عضو وصل می‌شود. نام مشابه به‌تنهایی هیچ‌وقت معیار اتصال نیست.
5. سرور با کنترل دسترسی، عضو را به داده‌های خودش، مربی را به حلقه‌های خودش و مدیر را به حلقه‌های واگذارشده محدود می‌کند.
6. حضور و غیاب، امتیازها و پیشرفت مأموریت‌ها با ثبت تاریخچه و زمان تغییر همگام می‌شوند؛ تعارض تغییرات آفلاین نیز باید طبق قواعد مشخص حل شود.

### تصمیم‌های فنی برای جلوگیری از بازنویسی

- مدل‌های فعلی آفلاین باقی می‌مانند؛ آنلاین‌سازی تا زمان تصمیم جداگانه فعال نمی‌شود.
- پیش از پیاده‌سازی همگام‌سازی، شناسه‌های محلی باید در مهاجرت نسخه‌ای به شناسه‌های پایدار تبدیل شوند.
- کد دعوت، رمز، توکن ورود و اطلاعات حساس در فایل پشتیبان عمومی ذخیره نمی‌شوند.
- ارتباط اینترنتی باید از طریق API امن و پایگاه داده سمت سرور انجام شود؛ فایل‌های محلی یا کد حلقه به‌تنهایی مرز امنیتی نیستند.
- مدیر مجموعه آمار تجمیعی حلقه‌های مجاز را می‌بیند؛ جزئیات خصوصی عضو فقط در صورت داشتن مجوز روشن قابل دسترسی است.
